Azure access & authorization — complete reference · RBAC · Entra roles · service access models · identities · the other gates

1 · Azure RBAC core

◈Key terms

  • Azure RBAC — authorization built on Azure Resource Manager; fine-grained access to Azure resources.
  • Role assignment = security principal + role + scope. Grant = create it; revoke = delete it.
  • Security principal — user, group (transitive), service principal, or managed identity.
  • Permission types — Actions → control plane · DataActions → data plane.

⚙Two permission planes

Control plane · Actions
Manage the resource — create / delete / configure. Via ARM (management.azure.com).

Data plane · DataActions
Touch the data inside — read a blob, read a secret. Via the resource's own endpoint.

Control-plane * does NOT grant data access. (Same split as a router: control plane vs forwarding plane.)

?Can an Owner read the blobs?

No — by default. Owner manages the account (control) but can't read blobs (data) unless they also hold a data role (Storage Blob Data Reader) or the access key (if Shared Key enabled).

Most-tested RBAC idea. Same shape for VMs (manage ≠ OS login) and Key Vault (manage vault ≠ read secret).

⤵Scope, inheritance & who can assign

Who can assign? Needs Microsoft.Authorization/roleAssignments/write → Owner, User Access Administrator, or RBAC Administrator. Contributor cannot.

∑Role = equation · how access is evaluated

Actions− NotActions= controlDataActions− NotDataActions= data

NotActions is not a deny; another assignment can grant it back. RBAC is additive — effective = sum of all assignments.

Evaluation order (ARM):

  1. Token (incl. transitive group memberships).
  2. Gather role + deny assignments for the resource.
  3. Deny assignment applies? → blocked (first).
  4. Else: is the action in Actions − NotActions (or data)?
  5. If yes: conditions (ABAC) evaluated last → allow/deny.

Role definitions, assignments & deny assignments are stored globally.

2 · Azure RBAC roles vs Microsoft Entra roles

⇄Two separate role systems

Don't overlap by default. A Global Administrator (Entra) is NOT an Owner in Azure — until they elevate access (Entra ID → Properties) → granted User Access Administrator on all subscriptions at the root. Both systems integrate with PIM.

Name traps: Azure Owner ≠ Entra Global Administrator · Azure User Access Administrator ≠ Entra User Administrator. Rule: "service + Reader/Contributor/Owner" = Azure RBAC; plain "X Administrator" over the tenant = Entra role.

3 · Service access models — each resource adds its own

🔑Key Vault — two authorization models

Two planes, controlled independently:

  • Control plane — manage the vault (create, network, properties) → Azure RBAC (e.g. Key Vault Contributor).
  • Data plane — keys / secrets / certificates → pick one model per vault:
Azure RBAC (recommended)Access policy (legacy)
Wherecontrol + data planedata plane only, native to KV
Grant controlOwner / UAA onlyany Contributor can self-grant
PIM / deny✓✗
Scalebuilt-in data roles≤ 1024 entries/vault

RBAC data roles: Key Vault Administrator, Secrets User/Officer, Crypto User/Officer, Certificates Officer. RBAC is the default for new vaults (API 2026-02-01+). Key Vault Contributor manages the vault but can't read secrets.

🗄Storage — ways to authorize data

  • Microsoft Entra ID (Azure RBAC + ABAC) — recommended, use a managed identity. Blob / queue / table.
  • Shared Key — the account key; full access to everything; can be disabled (then only Entra / user-delegation SAS).
  • SAS — a signed URL granting limited, time-boxed access.
  • Anonymous public access — blob only; can be disabled.

◍Identities that receive access

Any of these can hold a role assignment:

  • User · Group (role is transitive to members, incl. nested) · Service principal (an app) · Managed identity.

⛔Other gates that can block you (even with the role)

  • Deny assignment — overrides any allow (above).
  • Azure Policy (Deny effect) — blocks non-compliant resources; separate from RBAC.
  • Resource lock — CanNotDelete / ReadOnly blocks even an Owner.
  • Network rules / firewall / private endpoint — you're authorized but the request can't reach the data.
  • Conditional Access — may block the sign-in before RBAC is even checked.

⧉Services with their own RBAC

Separate role systems (own data store + decision point):

  • Microsoft Entra ID, Exchange, Intune, Defender, Compliance, Cost Management
  • Synapse RBAC · AKS (Kubernetes RBAC) · SQL roles

Azure RBAC ≠ any of these. Know that service-specific RBAC exists.

5 · Traps & where to inspect

!Exam traps & where to look

  • Control plane ≠ data plane (Owner can't read blobs / secrets; Contributor can't log into a VM).
  • Contributor can't assign roles. UAA = access only. RBAC Administrator = assignments but not deny assignments.
  • NotActions ≠ deny — real deny = a deny assignment (evaluated first, overrides).
  • Azure RBAC ≠ Entra roles; a Global Admin isn't an Azure Owner (must elevate).
  • Key Vault: access-policy mode lets a Contributor self-grant data access → use the RBAC model.
  • Storage: user delegation SAS (Entra) is secure; account/service SAS use the account key.
See it: Portal → any scope → Access control (IAM) → Roles.
az role definition list --name "Owner"
Get-AzRoleDefinition "Owner" | ConvertTo-Json
REST: …/roleDefinitions?$filter=type+eq+'BuiltInRole'&api-version=2022-04-01

Built-in JSON is read-only in the portal (Clone to base a custom role). Reference roles by their stable GUID in scripts (Reader = acdd72a7-3385-48ef-bd42-f606fba81ae7). Entra roles: Entra ID → Roles & administrators / Microsoft Graph.
