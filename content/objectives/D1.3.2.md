## In one sentence
A resource lock is a guardrail that stops anyone — including Owners — from deleting or changing a subscription, resource group, or resource, no matter what their RBAC role allows.

## Why it exists
RBAC answers "who is allowed to do this." Locks answer "should *anyone* be able to do this right now." They are different axes. You already think this way with firewalls: an allow rule says a host *may* talk, but you still drop traffic to a box under maintenance regardless of the rule. A lock is that drop rule for the control plane. A production database can be owned by five admins who all legitimately have delete rights, and you still never want it deleted by accident. ==The lock overrides every one of their permissions.==

## What actually matters
The whole objective sits on this one table. Learn it cold.

| | ==@CanNotDelete== (portal: Delete) | ==@ReadOnly== (portal: Read-only) |
|---|---|---|
| Read operations | Allowed | Allowed |
| Modify / write operations | Allowed | ==!Blocked== |
| Delete operations | ==!Blocked== | ==!Blocked== |
| Plane it acts on | ==!Control plane only== | ==!Control plane only== |
| Protects data (blob contents, VM guest/disk data)? | No | No |
| Who can set / remove | Owner + User Access Administrator | Owner + User Access Administrator |
| Permission required | `Microsoft.Authorization/locks/*` | `Microsoft.Authorization/locks/*` |

- **Two levels only.** Portal calls them **Delete** and **Read-only**; the CLI/PowerShell/API call them **CanNotDelete** and **ReadOnly**. Know both names — the exam mixes them. CanNotDelete = read + modify, no delete. ReadOnly = read only, like the Reader role.
- **Inheritance flows down and most-restrictive wins.** A lock on a resource group applies to every resource inside it, including ones you add later. If a parent has ReadOnly and a child has CanNotDelete, the child is ==effectively ReadOnly==. A Delete lock on one resource blocks deletion of its whole resource group — no partial delete.
- **Control plane only, never data plane.** A lock stops ARM operations (requests to `management.azure.com`). It does not touch data. A ReadOnly lock on a storage account does **not** stop blobs being read, written, or deleted — those go to the data-plane endpoint.
- **Who can set them:** needs `Microsoft.Authorization/locks/*` (or `Microsoft.Authorization/*`). Only **Owner** and **User Access Administrator** hold it by default. ==!Contributor cannot create or delete locks.==
- **ReadOnly has sharp edges.** It blocks POST operations that look harmless: listing storage account keys, starting/restarting a VM, getting Application Gateway backend health, assigning RBAC roles scoped to the account. A read-only lock on a storage account forces users without keys onto Entra ID credentials.
- **You cannot lock a management group.** Locks apply to ==subscription, resource group, and resource scopes only.==

## Where it lives
- **Portal:** on a resource group or resource, **Settings > Locks > Add**. On a subscription the blade is called **Resource locks** (Subscriptions > *name* > Settings > Resource locks). Give it a name and pick Delete or Read-only.
- **Azure CLI:** `az lock create --name LockGroup --lock-type CanNotDelete --resource-group myRG` (add `--resource-name` / `--resource-type` to lock a single resource). List with `az lock list`, remove with `az lock delete --ids {id}`.
- **Azure PowerShell** (module `Az.Resources`): `New-AzResourceLock -LockName LockGroup -LockLevel CanNotDelete -ResourceGroupName myRG`. Read with `Get-AzResourceLock`, remove with `Remove-AzResourceLock -LockId {id}`.
- **ARM/Bicep:** resource type `Microsoft.Authorization/locks`, property `level` set to `CanNotDelete` or `ReadOnly`.

## Exam traps
- **"ReadOnly protects my data."** No. ==!ReadOnly does NOT protect data-plane operations.== A ReadOnly lock on a storage account still lets anyone with keys or data-plane rights delete every blob. If the question asks how to protect *data*, the answer is ==+soft delete / immutability / RBAC==, not a lock.
- **"Contributor removed the lock."** Contributor cannot. Only ==+Owner and User Access Administrator== (the holders of `Microsoft.Authorization/locks/*`). A distractor will offer Contributor.
- **"My Owner role lets me delete it anyway."** It does not — ==!a lock beats your Owner role.== You must remove the lock first, which itself needs the `locks/*` permission.
- **CanNotDelete vs ReadOnly naming.** A question in CLI terms uses CanNotDelete/ReadOnly; a portal screenshot says Delete/Read-only. ==Same two things.==
- **"Lock the management group."** Not possible. If a scenario needs governance above subscription level, that is ==+Azure Policy or management-group RBAC==, not a lock.
- **Deleting a resource group with any locked resource inside fails entirely** — there is ==!no partial delete.== Expect a scenario where one locked VM blocks the whole RG cleanup.
- **A lock does not stop subscription cancellation.** Cancelling a subscription is ==!not blocked by a resource lock.==
- **ReadOnly blocks "can't I just restart it?"** Starting or restarting a VM is a POST, so ==!ReadOnly blocks it.== CanNotDelete does not.

### Managed applications: locks you did not set
Some services (Azure Databricks is the example) deploy into a **locked** managed resource group you do not own. You cannot delete that lock directly — a system application owns it. Delete the *service* instead, which removes the locked group with it. Worth recognising so a "the lock won't delete" scenario does not look like a bug.

![Azure Databricks service selected in the portal](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/media/lock-resources/select-service.png){The deployed service — its infrastructure lives in a separate, locked managed resource group}

![Managed Resource Group link in the portal](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/media/lock-resources/show-managed-group.png){The Managed Resource Group link points to the locked infrastructure group you can only delete indirectly}

![Delete option for the selected service](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/media/lock-resources/delete-service.png){Delete the service itself to remove everything, including the locked managed resource group}

## Skip
The lock-resources article lists ~20 service-specific side effects (AKS portal access, Azure Machine Learning autoscale, PostgreSQL vnet locks, Site Recovery stale links, Databricks managed resource groups, deployment-history 800-count failures). You do not need to memorise that list. Learn the **pattern** instead: ReadOnly blocks any POST/write, and that catches a few operations that do not look like writes (list keys, start VM, backend health). Also skip the full ARM/Bicep template-scope mechanics (when to set the `scope` property) and the Python/REST SDK examples entirely — AZ-104 tests the concept, the two level names, who can set them, and control-plane-not-data-plane, not SDK syntax.
