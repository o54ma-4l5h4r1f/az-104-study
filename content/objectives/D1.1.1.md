## In one sentence
Create user accounts and the groups you bundle them into, inside Microsoft Entra ID. Entra ID is the cloud directory that fronts every Azure sign-in.

> **Exam core.** Keep three axes separate: a user's ==@type== (Member vs Guest), a group's ==@membership type== (Assigned vs Dynamic), and a user's ==@identity source== (cloud, synced, invited) are independent — a question that conflates them is testing exactly this. Deleted users soft-delete for ==30 days==, then ==auto-purge== permanently. Any ==@Dynamic== membership needs a ==@Microsoft Entra ID P1== license. On the Assignments tab at creation you can seed a user into up to ==20 groups==, up to ==20 roles==, and ==one administrative unit==.

## Why it exists
You already know the identity primitives: an account authenticates, a group bundles accounts so you grant access once instead of per-person, least privilege says keep membership tight. None of that is new. What *is* new is the Entra-specific shape of it. Entra is not Active Directory. There are no OUs, no GPOs, and group behaviour is split along two axes Windows AD never had: a group's **type** (what it is for) and its **membership type** (how members get in). Those two axes, plus where a user's account actually comes from, are the whole objective. Get them exact and this bullet is free marks.

## Mental model
Two independent choices define a user, and two independent choices define a group. Pick wrong on the group axes and you often cannot fix it later — group *type* is permanent.

## What actually matters

The two user axes and the two group axes, as tables first — these four contrasts are where the marks are.

| User axis | Options | What it means |
|---|---|---|
| **Type** | ==@Member== / ==@Guest== | Member = your own org's person. Guest = external, cut-down default permissions. Set at creation, changeable later on the user's **Identity** properties. |
| **Source** | Cloud / Synced / Invited | Cloud = born in Entra (source *Microsoft Entra ID*). Synced = born in on-prem AD (source *Windows Server AD*). Invited = guest (source *Invited user*). ==!You cannot edit a synced user's identity fields in Entra== — change them on-premises and wait for sync. |

| Group axis | Options | What it means |
|---|---|---|
| **Type** (==!permanent==) | Security / Microsoft 365 | Security = access to resources and apps. M365 = adds shared mailbox, calendar, SharePoint site, files. ==!You cannot convert one to the other== — delete and recreate. |
| **Membership type** (changeable) | Assigned / Dynamic User / Dynamic Device | Assigned = add members by hand. Dynamic User = rule on user attributes. Dynamic Device = rule on device attributes, ==@Security groups only==. Any Dynamic needs ==@Entra ID P1==. |

**1. Source decides where you edit a user.** Cloud and guest users you edit in Entra. A directory-synced user's job and identity fields are read-only in the Entra portal — change them on-premises and wait for the next sync. Cloud Sync is the current recommended sync agent; Connect Sync is for complex cases (device sync, groups over 50,000 members).

**2. Deletes are soft for 30 days.** A deleted user sits on the ==@Deleted users== page and is restorable for ==30 days==, then purged automatically and permanently. Deleting a user frees any licenses it held.

**3. You can seed membership at creation.** On the user's **Assignments** tab you can drop the new user into up to ==20 groups== and ==20 roles==, plus ==one administrative unit==.

**4. Security group members are not only users.** They can be users, devices *and* service principals.

## Where it lives

**Portal (Microsoft Entra admin center, entra.microsoft.com):**
- Users: **Entra ID > Users > All users > New user > Create new user** (or **Invite external user**). Deleted ones: **Users > Deleted users**.
- Groups: **Entra ID > Groups > All groups > New group**.

The same blades exist in the **Azure portal** under **Microsoft Entra ID**. Creating users needs **User Administrator**; inviting guests needs **Guest Inviter**; groups need **Groups Administrator** or **User Administrator**.

**Microsoft Graph PowerShell** (module `Microsoft.Graph.Users` / `Microsoft.Graph.Groups`):

```
New-MgUser -DisplayName "Chris Green" -UserPrincipalName "chris@contoso.com" `
  -MailNickname "chris" -AccountEnabled `
  -PasswordProfile @{ Password = "<pwd>"; ForceChangePasswordNextSignIn = $true }

New-MgGroup -DisplayName "Northwest Sales" -MailEnabled:$false `
  -MailNickname "nwsales" -SecurityEnabled
```

**Azure CLI:**

```
az ad user create --display-name "Chris Green" \
  --user-principal-name chris@contoso.com --password <pwd>

az ad group create --display-name "Northwest Sales" --mail-nickname nwsales
```

Note the old `AzureAD` / `MSOnline` PowerShell modules (`New-AzureADUser`) are retired — Microsoft Graph PowerShell is the current one.

## Exam traps

- **Group type is a one-way door.** "Change this Microsoft 365 group to a security group" — the only correct answer is ==+delete and recreate==. Membership type, by contrast, *can* be changed after creation.
- **Dynamic Device is Security-only.** "Dynamic Device" membership on a *Microsoft 365* group is ==!the wrong answer==. M365 groups support ==+Dynamic User==, not Dynamic Device.
- **Dynamic membership = P1.** On a free/Microsoft Entra ID Free tenant, dynamic rules are ==!not available==; only ==+Assigned==. Watch for license as the gotcha.
- **Synced users are read-only in Entra.** "Update the job title of a directory-synced user" → do it in ==+on-premises AD== and wait for sync, ==!not in the Entra portal==.
- **Soft delete is 30 days, automatic purge.** Distractors will offer ==!14 days==, ==!90 days==, or ==!permanent immediately==. It is ==+30 days==, then automatic permanent deletion.
- **Guest ≠ a UPN in your domain.** Inviting a guest uses *their own email*; it does ==!not== create `guest@yourdomain`. Creating a user and setting type to Guest is a different path.
- **Role-assignable groups** force **Assigned** membership and need P1/P2 plus Privileged Role Administrator — you ==!cannot make them dynamic==.
- **Nested groups:** only Security groups nest; you cannot put a security group inside a Microsoft 365 group, and nested members do ==!not inherit== the parent's assigned app/resource access or licenses.
- **Security group members** can be users, devices *and* service principals — not just users.
