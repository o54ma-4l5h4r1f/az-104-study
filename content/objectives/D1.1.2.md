## In one sentence
User and group properties are the editable attributes on an Entra object — the profile fields on a user, the settings on a group, and the ==@membership rule== that computes a dynamic group's members.

## Why it exists
A user object is a bag of attributes, and those attributes drive everything downstream: licence assignment, Conditional Access, who lands in which group. You already think in attribute-based access control. This is the same idea — a rule that reads `user.department` and grants membership is a dynamic filter, not a static list. The job here is keeping those attributes correct, editing them in the right place, and writing the rule that reads them.

> Group *type* (Security vs Microsoft 365), *membership type* (Assigned / Dynamic User / Dynamic Device), and the fact that synced users are read-only in Entra are all taught in **D1.1.1** — cross-reference, don't re-learn. This page is only the delta: *editing* the properties and *writing* the rule.

## What actually matters

**1. Two ways into one user, one way to edit many.** Open a single user and use the ==@Edit properties== button (full tabbed edit view) or the ==@Properties tab== (read-only until you click the pencil on a category). To touch many at once, tick rows and choose **Edit** — but that is where the ==!60-user cap== and the field subset bite.

![Screenshot of a selected user overview page with the Edit properties and Properties options highlighted.](https://learn.microsoft.com/en-us/entra/fundamentals/media/how-to-manage-user-profile-info/user-profile-overview.png){Two ways in: the Edit properties button, or the Properties tab.}

![Screenshot of a user's details in the tabbed edit view with categories and the Save button highlighted.](https://learn.microsoft.com/en-us/entra/fundamentals/media/how-to-manage-user-profile-info/user-profile-properties-tabbed-view.png){Edit properties opens every field in edit mode, grouped by category: Identity, Job information, Contact info, Settings.}

![Screenshot of the Properties tab single-page view with the pencil edit icons highlighted.](https://learn.microsoft.com/en-us/entra/fundamentals/media/how-to-manage-user-profile-info/user-profile-properties-single-page-view.png){The Properties tab shows everything read-only; the pencil per category switches that section to edit.}

**2. Property categories, and what is editable for whom.** User fields group into four categories. For a cloud user you can edit them all. For a ==!directory-synced user== the identity/job/contact attributes are mastered on-prem and read-only in Entra (see D1.1.1) — only the cloud-side settings stay editable.

| Category | Example fields | Cloud user | Synced user |
|---|---|---|---|
| **Identity** | First/Last name, Display name, User Principal Name, User type | Editable | ==!Read-only== — edit in on-prem AD |
| **Job information** | Job title, Department, Company, Employee ID, Manager | Editable | ==!Read-only== — synced from AD |
| **Contact info** | Email, phone, street, city, state, country | Editable | ==!Read-only== — synced from AD |
| **Settings** | Usage location, Block sign-in, Account enabled | Editable | ==+Editable== (cloud-side attribute) |

**3. Bulk edit is capped at 60 and exposes a subset.** Select up to ==!60 users==, click **Edit**, and you can only set shared fields — City, Department, Job title, Usage location and similar. Everything else is per-user. Bulk *create / invite / delete / download* are separate operations driven by CSV uploads, not this Edit panel.

![Screenshot of the multiple-user edit options in the Microsoft Entra admin center.](https://learn.microsoft.com/en-us/entra/fundamentals/media/how-to-manage-user-profile-info/multiple-user-settings.png){Select up to 60 users, then Edit to change shared attributes in one pass.}

![Screenshot of the multiple-user edit-properties options.](https://learn.microsoft.com/en-us/entra/fundamentals/media/how-to-manage-user-profile-info/multiple-user-settings-edit.png){Bulk Edit properties exposes only a fixed subset — City, Department, Job title, Usage location and similar.}

**4. The dynamic membership rule is the group-property delta.** Syntax is `user.property -operator "value"`, for example `user.department -eq "Sales"`. The rule builder takes up to **five expressions** and user groups only; device rules and anything more complex go in the text box. Know the operators — they are a frequent distractor source:

| Operator | What it does | Example |
|---|---|---|
| `-eq` / `-ne` | equals / not equals | `user.department -eq "Sales"` |
| `-startsWith` | string prefix match | `user.userPrincipalName -startsWith "adm"` |
| ==!`-contains`== | ==!string *partial* match — NOT list membership== | `user.department -contains "ale"` |
| `-match` | regex match | `user.displayName -match "^A"` |
| `-in` / `-notIn` | value is in a supplied list | `user.department -in ["Sales","IT"]` |
| ==@`-any`== / ==@`-all`== | quantifier over a multi-value property | `user.assignedPlans -any (assignedPlan -eq "…")` |

For "is this user in one of these departments" use ==+`-in`==, not `-contains`. For multi-value properties (collections) use ==+`-any`/`-all`== with the per-element syntax.

![Screenshot of the dynamic membership rule builder with the Add expression action highlighted.](https://learn.microsoft.com/en-us/entra/identity/users/media/groups-dynamic-membership/update-dynamic-group-rule.png){The rule builder — up to five expressions, user groups only. Device and complex rules go in the text box.}

**5. Custom security attributes need their own admin roles.** These are tenant-defined key-value pairs (Boolean / integer / string) you attach to users or apps. ==!User Administrator cannot manage them==, and even a Global Administrator sees nothing until granted ==@Attribute Definition Administrator== (to create the definitions) and ==@Attribute Assignment Administrator== (to set values). They are excluded from SAML and JWT token claims and are unsupported in Entra Domain Services.

![Screenshot of the Custom Security Attributes dialog showing String, Integer, and Boolean types.](https://learn.microsoft.com/en-us/training/wwl-sci/create-configure-manage-identities/media/custom-security-attributes.png){Custom security attributes are String, Integer, or Boolean — and need their own admin roles to see or set.}

## Where it lives
- **Portal (user):** Microsoft Entra admin center (entra.microsoft.com) > **Entra ID > Users** > select user > **Edit properties** (or the **Properties** tab, pencil per category). Bulk: **Users > Bulk operations** (create/invite/delete/download) or select rows > **Edit**.
- **Portal (group):** **Entra ID > Groups** > select group > **Properties**, and **Dynamic membership rules** for the rule.
- **Portal (tenant-wide):** **Entra ID > Users > User settings** (Global Administrator) for app registration, group creation, guest-access restrictions.
- **CLI:** `az ad user update --id {upn} --set department=Sales` · `az ad group member add/remove`.
- **PowerShell (Microsoft.Graph module):** `Update-MgUser -UserId {id} -Department "Sales"` · `Update-MgGroup -GroupId {id} -MembershipRule "..." -MembershipRuleProcessingState "On"`. The old `AzureAD`/`MSOnline` modules are retired.

![Screenshot of the Microsoft Entra user settings options.](https://learn.microsoft.com/en-us/entra/fundamentals/media/how-to-manage-user-profile-info/user-settings.png){Tenant-wide User settings (Global Administrator) — app registration, "users can create security groups", guest-access restrictions.}

## Exam traps
- ==!`-contains` is a string partial match, not collection membership.== For "is in this list" use ==+`-in`==; for multi-value properties use ==+`-any`/`-all`== with the per-element syntax. This substitution is a classic distractor.
- ==!Bulk edit limit is 60==, not unlimited — a distractor may offer a larger number, or imply every field is editable in bulk. Only the fixed subset is.
- ==!Custom security attributes are not managed by User Administrator.== They need ==+Attribute Definition Administrator== / ==+Attribute Assignment Administrator==, and they never appear in token claims. If a scenario grants User Administrator and expects custom-attribute access, that is the trap.
- **Editing a synced user in Entra is blocked for identity/job/contact fields** — change them in on-premises AD and wait for sync (full treatment in D1.1.1). Settings like Usage location stay editable in Entra.
- **"Add a specific user to a dynamic group" is always wrong.** Membership is computed — edit the user's attribute and the rule re-evaluates.
