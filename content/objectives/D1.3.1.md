## In one sentence
Azure Policy checks every resource against rules you write and either blocks the non-compliant change, flags it, or fixes it — judged on the resource's configuration, never on who made it.

> **Exam core.** Policy governs resource ==shape== / compliance; RBAC governs ==who==. Effect evaluation order: ==@disabled → append/modify → deny → audit → auditIfNotExists → denyAction==. Only ==@Modify== and ==@DeployIfNotExists== effects need a managed identity — because only those two change or deploy a resource.

## Why it exists
RBAC answers "can this person do this?" Policy answers "is the result allowed to exist?" You already own RBAC — least privilege, role at a scope. Policy is the other half. An Owner has permission to create anything, but Policy still blocks a storage account in the wrong region or without the required tag. Think of it as a firewall for resource *shape* rather than for traffic: a rule set that inspects the resource and allows, denies, or rewrites it. It runs on new deployments and sweeps existing resources on a cycle, so drift gets caught too.

## Mental model
Three nested objects. You write a **definition** (one rule, one effect), optionally bundle several into an **initiative**, then **assign** that to a scope. The assignment is the only thing that actually does anything.

## What actually matters
- **One effect per definition.** The common ones: **Deny** (block the request), **Audit** (log a warning, allow it), **Append** (add a field to the request), **Modify** (add/change/remove properties or tags), **DeployIfNotExists** (DINE — deploy a related resource), **AuditIfNotExists** (AINE — flag when a related resource is missing). Evaluation order: *disabled → append/modify → deny → audit → manual → auditIfNotExists → denyAction last*.
- **Only Modify and DeployIfNotExists need a managed identity**, because they change or deploy resources. Deny, Audit, Append and the IfNotExists *audit* variant do not. One assignment gets exactly one managed identity (system- or user-assigned).
- **AINE and DINE check a *related* resource, not the target's own properties.** `audit` looks at the resource itself; `auditIfNotExists` looks for a child/extension resource (e.g. a diagnostic setting) and flags its absence.
- **Compliance is evaluated** on create/update, on a new or changed assignment, and on a standard cycle every **24 hours**. A fresh assignment can take up to **30 minutes** to take effect. Force a scan with `az policy state trigger-scan`.
- **Remediation fixes *existing* resources** — only for Modify and DeployIfNotExists. New/updated resources are remediated automatically; existing ones need a remediation task. The assignment's managed identity must hold the RBAC roles the definition lists in `roleDefinitionIds`.
- **enforcementMode = DoNotEnforce** is "what-if": evaluate and report compliance without the effect firing or writing to the activity log. It is *not* the same as the `disabled` effect, which skips evaluation entirely.

## Where it lives
- **Portal:** Azure portal > search **Policy** > **Definitions** (browse built-ins / create custom), **Assignments** (**Assign policy** or **Assign initiative**), **Compliance** (dashboard), **Remediation** (tasks). Managed identity is set on the assignment wizard's **Remediation** tab.
- **Azure CLI:** `az policy definition create`, `az policy set-definition create` (initiative), `az policy assignment create --mi-system-assigned --location {region}`, `az policy state trigger-scan`, `az policy state list`, `az policy remediation create`.
- **Az PowerShell:** `New-AzPolicyDefinition`, `New-AzPolicySetDefinition`, `New-AzPolicyAssignment -IdentityType SystemAssigned -Location {region}` (module **Az.Resources**); `Get-AzPolicyState`, `Start-AzPolicyRemediation` (module **Az.PolicyInsights**).

It is ==!not first-match== — every gate is checked, so a question can hide the real blocker behind a plausible one.

> See this gate together with the whole domain in the [Domain 1 diagrams](../diagram/D1.html) — the scope spine, the identity-to-access bridge, and a map of the Azure controls that look alike.

- **"An Owner can't create the resource — why?"** ==!Policy Deny, not RBAC.== Permission and compliance are separate gates. RBAC is checked first; if it passes, Policy still decides.
- **Which effects need a managed identity?** Only ==@Modify== and ==@DeployIfNotExists==. If an answer lists Deny or Audit as needing an identity, it is wrong. Append changes the request but is synchronous and needs no identity.
- **Remediation applies only to Modify and DeployIfNotExists.** You cannot "remediate" a Deny or an Audit policy — Deny blocks up front, Audit only reports.
- **Initiative = policy set = `policySet`/`PolicyDefinition` set in CLI/PowerShell.** Same thing, three names.
- **Audit does not block.** ==!It writes a warning== to the activity log and marks the resource non-compliant. ==+Deny is the one that blocks.==
- **Exclusion vs exemption.** `notScopes` (excluded scope) is set at assignment time. An **exemption** is created afterwards as a child object (category **Mitigated** or **Waiver**) and ==!still counts toward the compliance total==.
- **Assign at a management group, but only resources at subscription/resource-group level are evaluated.** The management group itself is not a "resource."
- **enforcementMode `DoNotEnforce`** still lets you run remediation tasks for DINE, and it is ==!different from the `disabled` effect== (which skips evaluation).
- **Layering is cumulative-most-restrictive.** Two overlapping Deny assignments both apply; the only way out is to exclude the scope or edit the denying assignment.

### Policy vs RBAC — the classic trap
The single most tested confusion in this objective. ==Policy judges the resource; RBAC judges the identity.== They are separate gates in the same pipeline — RBAC runs first, and if it passes, Policy still gets a veto on the result.

This objective is taught through the **Azure Policy initiatives** module, which is really a *Microsoft for Sovereignty* module. Skip **Unit 2, "Cloud Adoption Framework for Azure"** (flagged off-blueprint) and every mention of the sovereignty baseline, the `industry-policy-portfolio` GitHub repo, and compliance-framework mappings — none of that is on AZ-104. Skip the deep JSON authoring in the definitions unit: the full operators/conditions table, aliases, and policy functions (`ipRangeContains`, `addDays`, `current()`, count expressions). Know the shape — `if`/`then`, `allOf`/`anyOf`, `field`, `effect` — and move on. Skip **Resource Provider modes** (`Microsoft.Kubernetes.Data`, `Microsoft.KeyVault.Data`, etc.) and the control-plane/data-plane deep dive beyond "Policy is in the control plane, after RBAC." Skip the **Event Grid** reaction pattern and the full eight-step **safe-deployment ring** framework — know only that `enforcementMode = DoNotEnforce` gives you a what-if dry run. Don't memorise the object-count limits table; at most remember that initiatives, assignments, and definitions each have per-scope caps.
