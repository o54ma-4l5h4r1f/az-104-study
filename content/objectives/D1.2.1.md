## In one sentence

Built-in Azure roles are Microsoft's pre-written bundles of resource permissions that you attach to a user, group, or app at a chosen scope — the same RBAC you already know, expressed as Azure Resource Manager `Actions` strings.

## Why it exists

You already know RBAC and least privilege. Skip the theory. The Azure-specific delta is three things.

First, you almost never write the permission list yourself. Azure ships **hundreds** of built-in roles (Owner, Reader, Virtual Machine Contributor, Storage Blob Data Reader, and so on). You pick one, you don't author it. Custom roles exist but are the exception.

Second, Azure splits permissions into a **control plane** and a **data plane** — managing the storage account is a different permission from reading the blobs inside it. That split is where most exam traps live.

Third — and this trips people from an on-prem AD background — **Azure RBAC is a completely separate system from Microsoft Entra roles**. A Global Administrator in the directory does not, by that fact, have any access to Azure resources.

## Mental model

A role definition is a permission equation, not a flat list. Effective access is what is left after the exclusions are subtracted, computed separately for management and for data.

## What actually matters

| Role | Can manage resources? | Can assign roles to others? | Notes |
|---|---|---|---|
| **Owner** | Yes (all) | **Yes** | Full control plus delegation |
| **Contributor** | Yes (all) | **No** | `*` minus `Microsoft.Authorization/*/Write` etc. |
| **Reader** | View only | No | Read-only on everything in scope |
| **User Access Administrator** | **No** | Yes | Manages *access only*, not the resources |

- **Owner vs Contributor is one axis: delegation.** Both manage everything. Only Owner can hand out roles. Contributor cannot, because its `NotActions` strips the `Microsoft.Authorization/*/Write` and `/Delete` operations.
- **Control plane ≠ data plane.** An Owner on a storage account can delete the account but, by default, cannot read the blobs in it. Reading blobs needs a data-plane role (e.g. Storage Blob Data Reader) or the access key. This is the single most-tested idea on this bullet.
- **RBAC is additive and has no deny by default.** Effective permission is the sum of all your assignments. Contributor at subscription + Reader at a resource group = still Contributor there. `NotActions` is **not** a deny — another assignment can grant the excluded action back.
- **Built-in roles have `AssignableScopes = "/"`** (the root), so any built-in role can be assigned at any scope. Custom roles must list their own assignable scopes. A tenant allows up to **5,000 custom roles**.
- **Azure RBAC and Microsoft Entra roles are different systems.** Entra roles (Global Administrator, User Administrator) manage the directory. Azure roles manage resources. Neither leaks into the other.

## Where it lives

- **Portal:** any resource, resource group, subscription, or management group > **Access control (IAM)**. The **Role assignments** tab shows who has what; the **Roles** tab lists every built-in (and custom) role and its permissions. "IAM" means *identity and access management* here.
- **Azure CLI:** `az role definition list` (inspect roles), `az role assignment create --assignee {id} --role "Reader" --scope {scope}`.
- **Azure PowerShell** (`Az.Resources` module): `Get-AzRoleDefinition`, `Get-AzRoleAssignment`, `New-AzRoleAssignment`.

## Exam traps

- **"Which role lets a user manage VMs but not grant others access?"** → ==+Contributor==, not Owner. Owner is the distractor; its only extra power is delegation.
- **"User Access Administrator can manage the resources."** → ==!False==. It manages *access* only (role assignments). It cannot create or edit resources. Owner is the role that does both.
- **"An Owner can read blob data / queue messages by default."** → ==!False==. Control-plane `*` does not include data actions. Expect a storage scenario where the correct answer is a `Storage Blob Data *` role or the access key.
- **"A Global Administrator automatically has access to Azure subscriptions."** → **False.** Entra and Azure RBAC are separate. (A Global Admin *can* elevate access to User Access Administrator at root, but that is a deliberate switch, not automatic.)
- **`NotActions` is a deny.** → **No.** It only subtracts from one role's wildcard. A second assignment can restore the action. Real denial comes from **deny assignments**, which are separate.
- **RBAC Administrator vs User Access Administrator:** the newer **Role Based Access Control Administrator** can create role assignments but *not* deny assignments or other access mechanisms — narrower than User Access Administrator. Watch for it as a distractor.

## Skip

- **Do not memorize the role catalog.** The built-in roles article lists hundreds across Compute, Networking, Storage, Containers, AI and more. Learn the four fundamentals (Owner/Contributor/Reader/User Access Administrator) and *recognize* that per-service data roles like Storage Blob Data Reader exist. The rest is a lookup, not a memory task.
- **Skip the 9-step access-evaluation flowchart, deny assignments internals, conditions, and "where RBAC data is stored" / global replication** in the overview article. Interesting, not on this bullet.
- **Skip the tool/SDK version table and the deep `AssignableScopes` examples** in the role-definitions article. Know the `Actions − NotActions` equation and the control/data split; ignore the version minutiae.
