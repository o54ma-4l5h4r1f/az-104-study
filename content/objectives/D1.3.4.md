## In one sentence
A resource group is a container that holds related Azure resources, and it is the boundary you delete, secure, lock, and tag as one unit.

## Why it exists
You need one handle for a set of resources that share a lifecycle. Think of it like a firewall object group or an OU: a named bucket so a rule, a permission, or a delete hits everything inside at once. A temporary dev environment goes in one group, and when you are done you delete the group and every resource in it goes with it. No orphaned disk, no forgotten public IP.

## Mental model
Every resource sits inside exactly one resource group, which sits inside one subscription, which (optionally) sits under a management group. RBAC, locks, and policy flow **downward** through that stack.

## What actually matters
- **One group, exactly one.** A resource belongs to one resource group at a time. You can move it, but it is never in two.
- **Delete is a cascade.** Deleting a resource group deletes every resource in it. There is no "keep contents" option.
- **The group's region is metadata only.** It sets where the group's metadata lives. Resources inside can sit in other regions.
- **Can't nest, can't rename.** No resource group inside another, and no rename after creation. Pick the naming convention up front, or create a new group and move resources.
- **RBAC, locks, tags, policy apply at the group and inherit.** One role assignment or one delete-lock on the group covers everything inside — this is why the group is the governance unit.
- **Moving is allowed but lossy.** You can move resources to another group or subscription. Role assignments, locks, tags, and policies do **not** follow — reapply them on the destination.

## Where it lives
**Portal:** `Azure portal > Resource groups > Create`. Inside a group: **Locks**, **Tags**, **Access control (IAM)**, **Delete resource group**, and the **Move** button (move to another resource group / subscription / region) on the resource list.

**Azure CLI:**

```azurecli
az group create --name myRG --location centralus
az group list --output table
az group delete --name myRG
az resource move --destination-group newRG --ids <id1> <id2>
az resource move --destination-group newRG --destination-subscription-id <subId> --ids <id>
```

**Azure PowerShell** (module `Az.Resources`):

```azurepowershell
New-AzResourceGroup -Name myRG -Location centralus
Get-AzResourceGroup
Remove-AzResourceGroup -Name myRG
Move-AzResource -DestinationResourceGroupName newRG -ResourceId <id>
```

## Exam traps
- **You cannot move a resource group itself to another subscription.** You move its *resources* into a group in the other subscription. That distinction is a classic distractor.
- **You cannot rename a resource group.** Create a new one and move resources in.
- **Role assignments, locks, tags, and policies do not transfer with a move.** Expect "which settings carry over?" — answer: none of those; reapply manually.
- **Cross-subscription move requires both subscriptions in the same Microsoft Entra tenant.** Different tenants means transfer billing ownership first.
- **A read-only lock blocks a move** (on source, destination, or subscription). A delete lock does ==!not== block the move itself but blocks deleting the group.
- **During a move both source and destination groups are locked up to ==@4 hours==** — no create/delete/update inside them. But the resources keep running; a moving VM has ==+no downtime==.
- **Group region vs resource region** gets tested. The group region is where metadata is stored, not where the resources run.
- Only **top-level resources** are specified in a move; child resources (like a VM extension) move with their parent and can't move alone.
